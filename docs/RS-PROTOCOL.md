## 2. ელექტრონული ურთიერთობის წინაპირობა

ელექტრონული ურთიერთობის სრულყოფილად განხორციელების მიზნით, RS-სა და პროვაიდერს შორის (პირველადი …) — *გვ. 4-ის დასაწყისი ეკრანზე არ ჩანს, დასამატებელია.*

### I — სისტემაში ჩართვის პროცედურა

1. ხელშეკრულების და თანდართული პროტოკოლის პროექტის განხილვა, შეთანხმება
2. RS-ის სატესტო სერვერზე პროვაიდერის დაშვება:
   - ა. დაცული კავშირის (**VPN**) გამართვა სატესტო სერვისისთვის
   - ბ. სერვისის აწყობა
3. სერვისის ტესტირება (სატესტო რეჟიმში ჩართვა)
4. მონაცემთა ბაზების პირველადი სინქრონიზაცია
5. ინფორმაციის ელექტრონულად გაცვლის შესახებ ხელშეკრულების და თანდართული პროტოკოლის გაფორმება
6. პროვაიდერის რეგისტრაცია RS-ის სისტემაში:

   | საიდენტიფიკაციო ნომერი | პროვაიდერის კოდი | პროვაიდერის დასახელება | საკონტაქტო პირის სახელი, გვარი | საკონტაქტო პირის ტელეფონები | ელექტრონული ხელმოწერის საჯარო ნაწილი | IP მისამართი |
   |---|---|---|---|---|---|---|

7. ქაღალდურ დოკუმენტს აქვს იურიდიული ძალა, ელექტრონულს არა (მიმდინარეობს შედარება)
8. მონაცემთა ბაზების საბოლოო სინქრონიზაცია ბოლო სინქრონიზაციიდან რეალურ სერვისზე გადასვლის თარიღამდე
9. რეალური სერვისი — მხოლოდ ელექტრონული დოკუმენტების მიმოსვლით

🧪 ჩვენთან: VPN RS-თან — ecommerce-ის relay; dev-ზე RS-ის ნაცვლად **სიმულატორი** (`rs-service …/simulator/keepz`); ხელმოწერა — signedXml (RS messages → Signed XML).

### II — RS-სა და პროვაიდერს შორის ერთჯერადი ელექტრონული სახით მონაცემთა გაცვლის პროცედურა

1. მონაცემთა გაცვლა ხორციელდება პროტოკოლის მიხედვით, ასევე შესაძლებელია ერთჯერადად მონაცემთა გაცვლა **XML, XLS, XLSX (EXCEL)** ან სხვა ფორმატებში ფაილის სახით, ორივე მხარის შეთანხმებით.
2. პროვაიდერი აწვდის ელექტრონულ მონაცემებს RS-ს:
   - ა. **კლიენტის შესახებ** — პროტოკოლის მიხედვით ან ხელმოწერილი XML ფაილის სახით:

     | საიდენტიფიკაციო ნომერი | პირადი ნომერი | დასახელება | პროვაიდერის კოდი | კლიენტის პირველი ანგარიშის გახსნის თარიღი |
     |---|---|---|---|---|

   - ბ. **წარდგენილი საინკასო დავალებების შესახებ** — XLS, XLSX (EXCEL) ფაილის სახით:

     | საიდენტიფიკაციო ნომერი | პირადი ნომერი | დასახელება | პროვაიდერის კოდი | საინკასო დავალების დადების თარიღი | საინკასო დავალების ნომერი | სახაზინო კოდი | თანხა |
     |---|---|---|---|---|---|---|---|

   - გ. **წარდგენილი ყადაღადადებული ანგარიშების შესახებ** — XLS, XLSX (EXCEL) ფაილის სახით:

## 3. RS-ისა და პროვაიდერის საინფორმაციო სისტემების დაკავშირება და ელექტრონული ურთიერთობის მეთოდი

- **რეგისტრაცია:** პროვაიდერი RS-თან ელექტრონული ურთიერთობის სისტემაში ჩართვის მიზნით უნდა დარეგისტრირდეს RS-ის საინფორმაციო სისტემაში. მიეთითება: საიდენტიფიკაციო ნომერი, პროვაიდერის დასახელება, საკონტაქტო პირის ტელეფონები, ელექტრონული ხელმოწერის საჯარო ნაწილი და **IP მისამართი**, რომელზეც და რომლიდანაც მიიღება შეტყობინებები. საკონტაქტო პირის სისტემასთან წვდომა დაიშვება სპეციალური იდენტიფიკატორების (კოდების) მეშვეობით, რომლის **განმეორება დაუშვებელია**.
- **კავშირი:** RS-ისა და პროვაიდერის სისტემებს შორის — **VPN**.
- **პაკეტური რეჟიმი:** კლიენტების, საინკასო დავალებების და ყადაღის შესახებ შეტყობინებები და სიები იგზავნება განსაზღვრული პერიოდულობით, **პაკეტებით (რამდენიმე ერთად)**. პროვაიდერის მიერ გამოგზავნილ პაკეტებს შორის ინტერვალი — **არანაკლებ 2 წამი**.
- **ფორმატი:** XML, შეტყობინების **მაქსიმალური სიგრძე 32 000 სიმბოლო**. სტანდარტული სახე:

```xml
<Signature xmlns="http://www.w3.org/2000/09/xmldsig#">
  [ელ. ხელმოწერის მონაცემები]
  <SignatureValue>sdfgsdfgdgdf345f=</SignatureValue>
  <Object Id="[ძირითადი მონაცემთა ბლოკის დასახელება]">
    [ძირითადი მონაცემთა ბლოკი]
  </Object>
</Signature>
```

ძირითადი მონაცემთა ბლოკის მნიშვნელობები აღწერილია შემდგომ თავებში. ელ. ხელმოწერის მონაცემები:

```xml
<SignedInfo>
  <CanonicalizationMethod Algorithm="http://www.w3.org/TR/2001/REC-xml-c14n-20010315" />
  <SignatureMethod Algorithm="http://www.w3.org/2000/09/xmldsig#rsa-sha1" />
  <Reference URI="#[ძირითადი მონაცემთა ბლოკის დასახელება]">
    <DigestMethod Algorithm="http://www.w3.org/2000/09/xmldsig#sha1" />
    <DigestValue>cL1hxNnQPIJqnpk5eg2sL0D3x6I=</DigestValue>
  </Reference>
</SignedInfo>
```

- **გადაცემა:** **SOAP web service**, ერთი მეთოდი — `AcceptMessage`, პარამეტრი და დასაბრუნებელი მნიშვნელობა — `string`.
  - RS-ის ვებ სერვისი: `[WebMethod] string AcceptMessage(string Login, string Password, string XMLMessage)`
  - პროვაიდერის ვებ სერვისი: `[WebMethod] string AcceptMessage(string XMLMessage)`
  - ამ მეთოდით ბრუნდება დადასტურება — **STATUS_REPORT**.

🧪 ჩვენთან:
- RS messages → details: **Signed XML** (`<Signature>…<Object Id="Clients">` — ჩანს RETURN_COLLECTION-ის signedXml-ში), **RS status report**, **Payload**.
- ყალბი ხელმოწერა → მთელი შეტყობინება უარყოფილია (**code 4**) — ტესტი გვაქვს (ყადაღა + ინკასო).
- ⏳ ჯერ არ გაგვიტესტავს: 32 000 სიმბოლოზე დიდი შეტყობინება; პაკეტი (რამდენიმე order ერთ შეტყობინებაში — სიმულატორის `rawOrder` items[] ამას იძლევა); 2 წმ ინტერვალი ჩვენს გამავალ პაკეტებს შორის.

## 4. შეტყობინების გაგზავნის და მიღების ზოგადი პროცედურა (სცენარი)

RS-ის მიერ პროვაიდერში შეტყობინებების გაგზავნისას:
1. ა) RS აყალიბებს გასაგზავნ შეტყობინებას და უკეთებს ელექტრონულ „ხელმოწერას“.
2. ბ) შემდეგ ხდება შეტყობინების გაგზავნა პროვაიდერში.

RS-ის სისტემა იძახებს პროვაიდერის ვებ სერვისს, აწვდის შეტყობინებას და **ელოდება მიღების დამადასტურებელ შეტყობინებას — ტექნიკურ დასტურს (status_report)**.

- **შეცდომა:** შეცდომის აღმოჩენისას ბრუნდება შეცდომის შესახებ შეტყობინება:
  - შეცდომა **მთლიან შეტყობინებაზე** → ბრუნდება შესაბამისი შეცდომა (მთელი შეტყობინება უარყოფილია);
  - შეცდომა **მონაცემთა ნაწილზე** → შეცდომა ბრუნდება **მხოლოდ იმ ნაწილზე**, დანარჩენი მონაცემი **ითვლება მიღებულად**.
- შეცდომის მიღების შემდეგ ტარდება ღონისძიებები მის აღმოსაფხვრელად; გასწორების შემდეგ იგზავნება **ახალი შეტყობინება მხოლოდ იმ ნაწილზე**, რომელზეც შეცდომა იყო და გასწორდა.
- **პრიორიტეტები:** ოპერაციები პროვაიდერმა უნდა განახორციელოს ოპერაციის შესრულების მომენტში RS-იდან მიღებული შეტყობინებების მიხედვით, **მე-7 პუნქტით გათვალისწინებული პრიორიტეტების** გათვალისწინებით.
- **კავშირის გაწყვეტა:** ვებ სერვისის გამოძახება ხდება **განმეორებით, დასტურის მიღებამდე**, ან ხდება დაკავშირება პროვაიდერის საკონტაქტო პირთან.
- **საქიროების შემთხვევა** (ფორს-მაჟორი): ურთიერთობა შეიძლება გაგრძელდეს წერილობითი ფორმით.
- იგივე პრინციპი მოქმედებს, როცა **პროვაიდერი აგზავნის** შეტყობინებას და RS არის მიმღები.

   - ბ) **საინკასო დავალებას** (კლიენტზე ბიუჯეტის მიმართ დავალიანების არსებობის შემთხვევაში);
   - გ) **ყადაღას**.
5. თუ კლიენტის გახსნის შესახებ შეტყობინება RS-ში შემოდის:

### ფორმატები

- თარიღი: `dd/mm/yyyy`; თარიღი და დრო: `dd/mm/yyyy hh:mm:ss`.
- ტექსტი: **Unicode UTF-8**.
- შეტყობინების ID — უნიკალური, ფორმატი **`SSSSSSSSSRRYYMMDDNNN`**:
  - `SSSSSSSSS` — გამგზავნის 9-ნიშნა საიდენტიფიკაციო ნომერი;
  - `RR` — მიმღების კოდი (RS = **00**; ბანკები: საქართველოს ბანკი 02, თიბისი 16, კრედო 17, ლიბერთი 13, … პეისერა 24, ფეიზი 32 და ა.შ.);
  - `YYMMDD` — გაგზავნის თარიღი;
  - `NNN` — დღის რიგითი ნომერი (1000-ზე მეტისას სიგრძე იზრდება).
  - მაგ.: საქართველოს ბანკი (ს/ნ 204378869), 2011-03-01, პირველი → `20437886900110301001`.

🧪 ჩვენი გამავალი messageId — `40561891500261109421` = `405618915` (Keepz-ის ს/ნ) + `00` (RS) + `261109` (2026-11-09) + `421` (რიგითი) ✅ ფორმატს ემთხვევა. ⏳ ტესტი: დღის განმავლობაში NNN იზრდება და არ მეორდება; ახალ დღეს თავიდან იწყება.
